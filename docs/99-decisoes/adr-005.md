# ADR-005 — Comunicação entre Features por meio da Camada Application

# Contexto

O projeto adota uma arquitetura baseada em Monólito Modular (ADR-001), organizada por Features (ADR-003).

Embora todos os módulos pertençam à mesma aplicação, era necessário definir regras claras para evitar dependências indevidas entre funcionalidades.

Sem essas regras, o acoplamento entre módulos tende a crescer ao longo do tempo, tornando a arquitetura difícil de manter e evoluir.

---

# Problema

Era necessário responder às seguintes questões:

* Como uma Feature acessa outra?
* É permitido acessar diretamente um Repository de outra Feature?
* É permitido manipular entidades pertencentes a outro módulo?
* Como preservar o encapsulamento de cada domínio?

---

# Decisão

Cada Feature expõe um **contrato público** por meio de sua camada **Application**.

Esse contrato representa a única forma oficial de interação entre módulos da aplicação.

Nenhuma Feature poderá acessar diretamente componentes internos de outra Feature.

---

# Regras

São permitidas apenas as seguintes dependências:

```text
Controller
        │
        ▼
Application Service
        │
        ▼
Use Case
        │
        ▼
Domain
        │
        ▼
Repository (Interface)
```

Quando uma Feature precisar utilizar funcionalidades de outra, deverá consumir exclusivamente os serviços expostos pela camada **Application**.

---

# Dependências Proibidas

Não é permitido:

* acessar diretamente Controllers de outra Feature;
* acessar diretamente Use Cases de outra Feature;
* acessar diretamente Repositories de outra Feature;
* utilizar implementações da camada Infrastructure de outra Feature;
* manipular entidades internas pertencentes a outro módulo;
* compartilhar detalhes de persistência.

Essas restrições preservam o isolamento entre os módulos.

---

# Contrato Público

Cada Feature deverá definir claramente quais operações disponibiliza para os demais módulos.

Exemplo conceitual:

```text
AnimalApplication

├── buscarAnimal()
├── registrarVenda()
├── registrarPrenhez()
└── atualizarCadastro()
```

Os módulos consumidores não devem conhecer como essas operações são implementadas.

Devem conhecer apenas o contrato disponibilizado.

---

# Benefícios

Essa decisão proporciona:

* baixo acoplamento;
* alta coesão;
* encapsulamento do domínio;
* facilidade para testes;
* facilidade para refatorações;
* possibilidade futura de extração para microsserviços.

Cada Feature passa a possuir uma API interna claramente definida.

---

# Alternativas Consideradas

## Acesso direto entre módulos

### Vantagens

* Implementação inicialmente mais simples.
* Menor quantidade de código.

### Desvantagens

* Forte acoplamento.
* Vazamento de regras de negócio.
* Dificuldade de manutenção.
* Dependências circulares.

**Decisão:** Não adotada.

---

## Comunicação pela camada Application

### Vantagens

* Módulos independentes.
* Contratos claros.
* Facilidade para evolução.
* Melhor organização do domínio.
* Preparação para futuras mudanças arquiteturais.

### Desvantagens

* Pequeno aumento na quantidade de classes.
* Necessidade de definir contratos públicos.

**Decisão:** Arquitetura adotada.

---

# Consequências Positivas

* Cada Feature torna-se responsável por sua própria consistência.
* Redução do acoplamento entre módulos.
* Facilidade para substituir implementações internas.
* Maior previsibilidade durante a evolução do sistema.
* Melhor alinhamento com o conceito de Monólito Modular.

---

# Consequências Negativas

* Algumas operações exigirão coordenação entre múltiplas camadas.
* Pequeno aumento da quantidade de código de orquestração.

# Observações

A camada **Application** representa a interface pública de cada Feature.

Toda comunicação entre módulos deverá ocorrer exclusivamente por essa camada, preservando o encapsulamento do domínio e evitando dependências indevidas entre componentes internos.

Qualquer exceção a esta regra deverá ser formalmente registrada por meio de uma nova ADR.
