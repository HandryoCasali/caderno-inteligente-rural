# Contexto

O domínio do **Caderno Inteligente Rural** é baseado no conceito de histórico de eventos associados a um Animal.

Durante a modelagem do domínio surgiu a necessidade de definir como o estado atual do Animal será persistido e recuperado.

Era necessário equilibrar simplicidade, desempenho e consistência do domínio.

---

# Problema

Existiam duas abordagens possíveis:

1. Recalcular o estado do Animal a partir de todos os eventos registrados.

2. Persistir diretamente o estado atual do Animal e utilizar os eventos apenas como histórico de negócio.

A decisão impacta diretamente:

* desempenho das consultas;
* simplicidade da implementação;
* modelagem do banco de dados;
* evolução do domínio.

---

# Decisão

O projeto persistirá explicitamente o estado atual do Animal.

Os eventos continuarão sendo registrados como histórico permanente do domínio, porém não serão utilizados para reconstrução completa do agregado a cada consulta.

O estado atual do Animal será atualizado durante a execução dos casos de uso responsáveis pelas alterações do domínio.

---

# Motivação

Embora o histórico de eventos seja extremamente importante para auditoria e rastreabilidade, o produto não possui requisitos que justifiquem a adoção de Event Sourcing.

Persistir diretamente o estado atual oferece:

* consultas mais rápidas;
* menor complexidade de implementação;
* menor consumo de recursos;
* simplicidade operacional.

Essa abordagem atende plenamente às necessidades do MVP.

---

# Funcionamento

Sempre que um caso de uso modificar o domínio:

1. O evento correspondente será registrado.
2. O Animal atualizará seu estado interno.
3. O Aggregate Root será persistido.
4. O histórico permanecerá disponível para consultas.

Dessa forma:

* o histórico preserva os fatos;
* o Animal representa o estado atual.

---

# Alternativas Consideradas

## Event Sourcing

### Vantagens

* Histórico completo.
* Reconstrução integral do estado.
* Auditoria avançada.

### Desvantagens

* Alta complexidade.
* Consultas mais custosas.
* Maior curva de aprendizado.
* Complexidade desnecessária para o contexto do projeto.

**Decisão:** Não adotado.

---

## Estado Persistido + Histórico

### Vantagens

* Simplicidade.
* Excelente desempenho.
* Facilidade para consultas.
* Implementação compatível com o domínio.

### Desvantagens

* Necessidade de manter sincronismo entre estado e histórico.

**Decisão:** Estratégia adotada.

---

# Consequências Positivas

* Consultas rápidas.
* Código mais simples.
* Banco de dados menos complexo.
* Evolução incremental do domínio.
* Facilidade para manutenção.

---

# Consequências Negativas

* O Aggregate Root passa a ser responsável por manter a consistência entre estado atual e histórico.
* Alterações indevidas no domínio podem gerar inconsistências caso as regras arquiteturais não sejam respeitadas.

# Observações

O projeto **não adota Event Sourcing**.

Os eventos representam fatos históricos do domínio e possuem finalidade de rastreabilidade e apoio às regras de negócio.

O estado atual será persistido diretamente no Aggregate Root, sendo atualizado sempre por meio dos casos de uso da aplicação.

Caso futuramente surjam requisitos que justifiquem reconstrução completa do estado a partir dos eventos, uma nova ADR deverá ser criada para reavaliar essa decisão.
