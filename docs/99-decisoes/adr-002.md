# Contexto

Após definir que o projeto adotará uma arquitetura baseada em Monólito Modular (ADR-001), tornou-se necessário estabelecer um padrão para organização do código interno da aplicação.

O projeto possui características que exigem uma arquitetura de fácil manutenção, alta coesão e baixo acoplamento, sem introduzir complexidade desnecessária.

Além disso, o sistema deverá evoluir continuamente ao longo dos próximos anos, mantendo um domínio consistente e independente das tecnologias utilizadas.

---

# Problema

Era necessário definir uma forma de organizar o código que permitisse:

* Separação clara de responsabilidades.
* Isolamento das regras de negócio.
* Independência em relação ao framework.
* Facilidade para testes.
* Evolução incremental da aplicação.
* Curva de aprendizado compatível com equipes pequenas.

Ao mesmo tempo, era importante evitar implementações excessivamente acadêmicas que aumentassem a complexidade sem trazer benefícios reais.

---

# Decisão

O projeto adotará uma **Clean Architecture pragmática**.

Os princípios fundamentais da Clean Architecture serão preservados, porém algumas adaptações serão realizadas para reduzir complexidade e melhorar a produtividade da equipe.

A arquitetura será orientada pelos seguintes princípios:

* O domínio representa o centro da aplicação.
* As regras de negócio não conhecem frameworks.
* Dependências sempre apontam para o domínio.
* Infraestrutura é um detalhe de implementação.
* Cada camada possui responsabilidades claramente definidas.
* Simplicidade prevalece sobre abstrações desnecessárias.

---

# Estrutura Arquitetural

Cada feature será organizada em camadas com responsabilidades bem definidas.

```text
Feature

├── api
├── application
├── domain
├── infrastructure
└── config
```

Cada camada possui uma única responsabilidade.

---

## API

Responsável pela comunicação com o mundo externo.

Exemplos:

* Controllers
* DTOs
* Mapeamentos HTTP
* Validações de entrada

A camada de API não contém regras de negócio.

---

## Application

Responsável por orquestrar os casos de uso.

Contém:

* Application Services
* Use Cases

Responsabilidades:

* Coordenar operações.
* Controlar transações.
* Buscar agregados.
* Persistir alterações.
* Integrar diferentes componentes.

A camada de aplicação não implementa regras de negócio.

---

## Domain

Representa o núcleo da aplicação.

Contém:

* Entidades
* Value Objects
* Aggregates
* Domain Services
* Interfaces de Repository
* Regras de negócio

O domínio não conhece:

* Spring
* JPA
* HTTP
* Banco de dados
* Frameworks

Toda regra de negócio deve residir nesta camada.

---

## Infrastructure

Responsável pelos detalhes técnicos.

Contém:

* Implementações de Repository
* Persistência
* Integrações externas
* Configurações específicas de tecnologia

A infraestrutura depende do domínio, nunca o contrário.

---

# Adaptações em relação à Clean Architecture tradicional

O projeto adota uma abordagem pragmática.

As seguintes simplificações foram aprovadas:

* Não utilizar abstrações sem benefício comprovado.
* Evitar interfaces desnecessárias.
* Utilizar Application Services como porta de entrada das features.
* Permitir Use Cases focados em uma única ação.
* Evitar padrões complexos sem necessidade do domínio.

---

# Alternativas Consideradas

## Arquitetura em Camadas Tradicional

### Vantagens

* Simplicidade inicial.
* Curva de aprendizado reduzida.

### Desvantagens

* Forte acoplamento.
* Crescimento de Services monolíticos.
* Baixa separação entre regras de negócio e infraestrutura.

**Decisão:** Não adotada.

---

## Clean Architecture Clássica

### Vantagens

* Excelente separação de responsabilidades.
* Independência tecnológica.
* Elevada testabilidade.

### Desvantagens

* Grande quantidade de abstrações.
* Curva de aprendizado elevada.
* Complexidade desnecessária para o contexto do projeto.

**Decisão:** Adaptada.

---

## Clean Architecture Pragmática

### Vantagens

* Baixo acoplamento.
* Alta coesão.
* Facilidade de manutenção.
* Independência tecnológica.
* Menor complexidade.
* Melhor produtividade.

### Desvantagens

* Exige disciplina para manter a arquitetura consistente.
* Algumas decisões dependem de julgamento técnico da equipe.

**Decisão:** Arquitetura adotada.

---

# Consequências Positivas

* Código organizado por responsabilidade.
* Regras de negócio protegidas.
* Independência em relação ao framework.
* Facilidade para testes.
* Evolução incremental.
* Maior legibilidade da aplicação.

---

# Consequências Negativas

* Exige conhecimento prévio da arquitetura.
* Requer disciplina para evitar vazamento de responsabilidades entre camadas.

# Observações

A arquitetura adotada prioriza simplicidade, clareza e evolução contínua.

A equipe deverá sempre privilegiar soluções simples e bem estruturadas antes de introduzir novos padrões ou abstrações.

A adoção de novos padrões arquiteturais deverá ser precedida por análise de impacto e registrada por meio de uma nova ADR, quando representar uma mudança estrutural na arquitetura do sistema.
