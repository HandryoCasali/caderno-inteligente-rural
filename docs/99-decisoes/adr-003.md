# Contexto

Após definir a adoção de um Monólito Modular (ADR-001) e de uma Clean Architecture pragmática (ADR-002), tornou-se necessário estabelecer como o código será organizado dentro da aplicação.

A organização do código influencia diretamente a produtividade da equipe, a facilidade de manutenção e a evolução do domínio ao longo do tempo.

---

# Problema

Era necessário escolher uma estratégia para estruturar o código-fonte que:

* facilitasse a localização de funcionalidades;
* reduzisse o acoplamento entre módulos;
* acompanhasse a evolução do domínio;
* evitasse a criação de camadas compartilhadas excessivamente grandes;
* favorecesse alta coesão.

---

# Decisão

O projeto adotará a organização **Feature First**.

Cada funcionalidade do domínio será implementada em um módulo próprio, contendo todos os elementos necessários para seu funcionamento.

Uma feature representa um conceito do negócio e possui autonomia organizacional dentro do monólito.

Exemplos de features:

* Animal
* Propriedade
* Usuário
* Autenticação
* Dashboard

Cada feature agrupa suas camadas de API, aplicação, domínio e infraestrutura.

---

# Estrutura Geral

A organização do backend seguirá o padrão:

```text
backend/
└── src/main/java/
    └── br/com/cadernorural/
        ├── animal/
        ├── propriedade/
        ├── usuario/
        ├── autenticacao/
        ├── dashboard/
        └── shared/
```

Cada diretório representa uma feature do domínio.

---

# Estrutura Interna da Feature

Cada feature deverá seguir uma estrutura semelhante à seguinte:

```text
animal/
├── api/
├── application/
├── domain/
├── infrastructure/
└── config/
```

### api

Responsável pela comunicação com clientes externos.

Exemplos:

* Controllers
* DTOs
* Mapeadores de entrada e saída

---

### application

Responsável por coordenar os casos de uso da feature.

Contém:

* Application Services
* Use Cases

---

### domain

Contém:

* Entidades
* Value Objects
* Interfaces de Repository
* Domain Services
* Regras de negócio

Representa o núcleo da feature.

---

### infrastructure

Contém:

* Implementações de Repository
* Persistência
* Configurações técnicas
* Integrações externas

---

### config

Configurações específicas da feature.

Seu uso deve ser excepcional e somente quando a configuração não fizer sentido em nível global.

---

# Comunicação entre Features

Cada feature deve ser considerada um módulo independente.

A comunicação deverá ocorrer exclusivamente por meio da camada de **Application**, conforme definido na ADR-005.

É proibido:

* acessar diretamente o Repository de outra feature;
* manipular entidades internas de outra feature;
* acessar Controllers de outra feature;
* depender de implementações da camada Infrastructure de outra feature.

Essa regra preserva o baixo acoplamento entre módulos.

---

# Shared

A pasta `shared` deve conter apenas componentes verdadeiramente compartilhados.

Exemplos:

* tratamento global de exceções;
* classes utilitárias realmente genéricas;
* configurações globais;
* componentes transversais (cross-cutting concerns).

A criação de novos componentes em `shared` deve ser criteriosa.

Sempre que possível, uma classe deve permanecer dentro da feature à qual pertence.

# Alternativas Consideradas

## Organização por Camadas

Exemplo:

```text
controller/
service/
repository/
entity/
```

### Vantagens

* Simples de compreender.
* Bastante difundida.

### Desvantagens

* Baixa coesão.
* Funcionalidades espalhadas pelo projeto.
* Crescimento desorganizado.

**Decisão:** Não adotada.

---

## Organização por Pacotes Técnicos

Agrupamento por tecnologia ou responsabilidade técnica.

### Vantagens

* Organização inicial simples.

### Desvantagens

* Dificulta localizar uma funcionalidade completa.
* Pouco alinhamento com o domínio.

**Decisão:** Não adotada.

---

## Organização por Features

### Vantagens

* Alta coesão.
* Baixo acoplamento.
* Melhor alinhamento com o domínio.
* Evolução incremental.
* Facilidade para localizar funcionalidades.

### Desvantagens

* Requer disciplina para evitar dependências cruzadas.
* Pode gerar duplicação controlada entre features, o que é aceitável quando reduz acoplamento.

**Decisão:** Arquitetura adotada.

---

# Consequências Positivas

* Código organizado conforme o domínio.
* Facilidade para evolução do produto.
* Melhor isolamento entre funcionalidades.
* Onboarding simplificado para novos desenvolvedores.
* Menor risco de criação de módulos excessivamente acoplados.

---

# Consequências Negativas

* Exige atenção para evitar crescimento indevido da pasta `shared`.
* Algumas funcionalidades poderão exigir coordenação entre múltiplas features.

# Observações

A organização por Features é uma decisão estrutural do projeto e deverá ser respeitada durante toda a evolução da aplicação.

Novas funcionalidades deverão ser adicionadas, preferencialmente, em uma feature existente. A criação de uma nova feature somente deverá ocorrer quando representar um novo conceito relevante do domínio.

O objetivo dessa abordagem é manter a arquitetura orientada ao negócio, favorecendo alta coesão, baixo acoplamento e facilidade de manutenção.
