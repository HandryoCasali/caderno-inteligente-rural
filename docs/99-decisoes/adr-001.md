# ADR-001 — Arquitetura Baseada em Monólito Modular

## Status

**Aceita**

---

## Data

01/07/2026

---

## Responsável

Handryo Casali

---

# Contexto

O **Caderno Inteligente Rural** é um SaaS destinado inicialmente a pequenos produtores de leite, com foco em simplicidade, rapidez de desenvolvimento e facilidade de evolução.

Embora o domínio possua diferentes áreas de negócio (Animais, Propriedade, Produção de Leite, Usuários, Autenticação etc.), todas fazem parte de um único produto, compartilhando o mesmo ciclo de vida e sendo mantidas por uma única equipe de desenvolvimento.

Nesse cenário, era necessário definir um modelo arquitetural que equilibrasse organização, escalabilidade e simplicidade operacional.

---

# Problema

Foram consideradas diferentes abordagens arquiteturais para estruturar a aplicação:

* Monólito tradicional.
* Monólito modular.
* Microsserviços.

A decisão deveria considerar:

* Complexidade de desenvolvimento.
* Facilidade de manutenção.
* Custo de infraestrutura.
* Escalabilidade futura.
* Curva de aprendizado.
* Produtividade de uma equipe pequena.

---

# Decisão

O projeto adotará uma arquitetura baseada em **Monólito Modular**.

A aplicação será implantada como uma única unidade executável, compartilhando o mesmo banco de dados, porém organizada internamente em módulos independentes orientados ao domínio.

Cada módulo (Feature) possuirá:

* sua própria camada de API;
* sua própria camada de aplicação;
* seu próprio domínio;
* sua própria infraestrutura;
* baixo acoplamento com os demais módulos.

As regras de comunicação entre módulos serão definidas por ADRs específicas.

---

# Motivação

A arquitetura de Monólito Modular foi escolhida por oferecer o melhor equilíbrio entre simplicidade e organização.

Ela permite:

* manter uma única aplicação em produção;
* reduzir custos de infraestrutura;
* simplificar deploys;
* facilitar depuração;
* manter transações únicas;
* organizar o código por domínio;
* reduzir acoplamento entre funcionalidades.

Além disso, essa arquitetura possibilita uma futura migração para microsserviços, caso exista necessidade real de escalabilidade organizacional ou técnica.

---

# Alternativas Consideradas

## Monólito Tradicional

### Vantagens

* Implementação simples.
* Baixa complexidade inicial.

### Desvantagens

* Alto acoplamento.
* Crescimento desorganizado.
* Dificuldade de manutenção.
* Baixa separação entre domínios.

**Decisão:** Não adotado.

---

## Microsserviços

### Vantagens

* Escalabilidade independente.
* Deploy independente.
* Isolamento entre serviços.

### Desvantagens

* Elevada complexidade operacional.
* Necessidade de comunicação distribuída.
* Maior custo de infraestrutura.
* Maior esforço de observabilidade.
* Maior complexidade para transações.

**Decisão:** Não adotado para o contexto atual.

---

## Monólito Modular

### Vantagens

* Organização por domínio.
* Baixo acoplamento.
* Alta coesão.
* Deploy simples.
* Banco de dados único.
* Transações consistentes.
* Facilidade para testes.
* Evolução incremental.

### Desvantagens

* Escalabilidade horizontal limitada à aplicação como um todo.
* Exige disciplina arquitetural para manter os módulos desacoplados.

**Decisão:** Arquitetura adotada.

---

# Consequências Positivas

* Organização clara do código.
* Separação entre domínios.
* Facilidade para onboarding de novos desenvolvedores.
* Menor custo operacional.
* Simplicidade de implantação.
* Evolução incremental da arquitetura.
* Possibilidade de extração futura de módulos para microsserviços.

---

# Consequências Negativas

* Todos os módulos compartilham o mesmo ciclo de deploy.
* Compartilhamento do mesmo banco de dados.
* Necessidade de disciplina para evitar dependências indevidas entre módulos.

# Observações

A adoção de um Monólito Modular não representa uma etapa intermediária obrigatória para microsserviços.

O objetivo desta arquitetura é atender às necessidades do produto com o menor nível possível de complexidade, preservando a qualidade do código e permitindo evolução contínua.

Uma eventual migração para uma arquitetura distribuída somente será considerada quando houver benefícios claros para o produto e para a equipe, sendo registrada por uma nova ADR.
